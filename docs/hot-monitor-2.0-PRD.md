## 一、背景与问题陈述

### 1.1 产品现状

AI 热点监控工具 1.0（Express + React SPA + SQLite）已完成核心闭环：用户配置关键词 → 系统每 30 分钟从 6+ 数据源抓取 → AI 过滤分析 → WebSocket/邮件通知。作为个人效率工具已可用，并沉淀了一个可被 AI 编程工具复用的 Agent Skills 技能包。

### 1.2 为什么做 2.0

1.0 是"能用"的教学项目，2.0 要变成"敢给别人用"的产品。当前阻碍产品化的四个问题：

| # | 问题 | 影响 |
|---|---|---|
| P1 | 系统无鉴权，任何能访问端口的人可删数据、烧 AI 额度 | 无法部署到公网，只能本机自用 |
| P2 | AI 调用量无硬约束（配额按入库计数而非按调用计数） | 关键词多、噪音多时 API 成本不可预测，用户不敢放开用 |
| P3 | 定时任务可并发重入；手动搜索接口同步等待长达数十秒 | 高峰期体验差，任务堆积导致重复扣费 |
| P4 | 数据源失效无感知（静默返回空结果）；前后端热度口径不一致 | 用户对"监控是否还在正常工作"失去信心；排序与展示矛盾损伤可信度 |

### 1.3 机会点

- AI 信息过载是普遍痛点，"让 AI 帮你盯热点"的需求从个人效率工具可扩展到内容创作者、投研、运营人群；
- 1.0 的双形态（Web 应用 + Agent Skill）已验证差异化：既是产品，也是 AI 生态的能力供应商。2.0 重构后，Agent Skill 与后端采集层同源，维护成本减半。

## 二、产品定位与目标

### 2.1 一句话定位

**为信息敏感型用户提供的关键词级全网热点雷达**：你只管订阅关键词，系统替你 7×24 盯着全网，只把"真实、相关、重要"的热点推给你。

### 2.2 目标用户与场景

| 用户画像 | 场景 | 核心诉求 |
|---|---|---|
| 内容创作者（博主/UP 主） | 监控自己领域的技术动态、竞品账号更新，抢热点选题 | 快（第一时间）、准（不要噪音） |
| 技术从业者/AI 爱好者 | 跟踪特定模型、框架、公司的动态 | 过滤假消息和软文，摘要省时间 |
| 运营/投研人员 | 监控品牌词、行业词在微博/搜索引擎的热度 | 中文源覆盖、热搜感知 |

### 2.3 产品目标与成功指标

| 类型 | 指标 | 目标值（2.0 上线后 90 天） |
|---|---|---|
| 北极星 | 单关键词日均有效热点推送数（用户未删除/未忽略的热点） | ≥ 3 条，且推送打开率 ≥ 40% |
| 质量 | AI 过滤准确率（抽样人工复核：被推热点中"确实相关且真实"占比） | ≥ 85% |
| 成本 | 单关键词单轮检查 AI 调用次数 | ≤ 25 次（硬上限，可配置） |
| 稳定性 | 定时任务按 30 分钟周期成功完成率 | ≥ 99%；单源故障不影响其他源 |
| 性能 | 首屏 LCP（Dashboard） | ≤ 2.5s；手动搜索响应（异步任务受理）≤ 1s |
| 可观测 | 数据源连续失效被发现的时间 | ≤ 1 个检查周期（30 分钟内告警） |

## 三、产品范围

### 3.1 In Scope（2.0 做）

- 1.0 全部功能的对等功能（关键词管理、多源监控、AI 分析、筛选排序、全网搜索、实时+邮件通知）
- 新增：API 鉴权、任务互斥与进度可见、AI 成本硬上限、数据源健康面板、搜索异步化
- 工程基座：Next.js + FastAPI 分离架构、PostgreSQL、OpenAPI 契约、Docker 一键部署

### 3.2 Out of Scope（2.0 明确不做，入 Backlog）

- 多用户体系与账号系统（schema 预留 `owner_id`，不做 UI 和注册登录）
- 每日/每周热点日报邮件（1.0 有未接线的 `sendDigestEmail`，2.0 不接线，待验证需求）
- 移动端 / 浏览器插件 / 微信与钉钉等更多通知渠道
- 全文检索（PG tsvector）、热点聚类与去重合并、趋势图表分析
- Agent Skills 包的功能升级（仅保持与后端 collectors 同源，不新增能力）

## 四、核心产品规则（业务规则书）

> 以下规则从 1.0 代码中提炼并修正，是 2.0 的**产品契约**，测试用例应逐条覆盖。规则编号在评审后冻结，后续变更需走需求变更流程。

### 4.1 监控与采集规则

| 规则 ID | 规则 | 说明 |
|---|---|---|
| R-101 | 检查周期：每 30 分钟对全部"激活"关键词执行一轮检查 | 暂停的关键词不参与；周期可在系统设置中调整 |
| R-102 | 任务互斥：同一时刻全局只允许一轮检查运行 | 定时与手动触发抢同一把锁；冲突时手动触发收到"检查进行中"提示及当前进度 |
| R-103 | 每关键词采集 6 个数据源并行抓取：Twitter、Bing、HackerNews、搜狗、B 站、微博热搜 | 单源失败不影响其他源；失败计入源健康记录 |
| R-104 | 账号检测优先：若关键词精确匹配 B 站 UP 主名（或粉丝 >1000 且名称包含关键词），直接拉取该 UP 主最新 10 条视频并赋予高优先级 | "监控人"与"监控话题"同一入口 |
| R-105 | 新鲜度：发布时间超过 7 天的内容丢弃；无发布时间的内容放行 | 搜索引擎结果通常无时间 |
| R-106 | 来源优先级：Twitter > 微博 > B 站 > HN > 搜狗 > Bing | 决定配额分配顺序 |
| R-107 | 微博源为"热搜榜匹配"：拉取微博实时热搜，与关键词双向包含匹配 | 只能发现已上热搜的话题，属监控而非搜索 |

### 4.2 AI 处理与过滤规则

| 规则 ID | 规则 | 说明 |
|---|---|---|
| R-201 | 查询扩展：每个关键词由 AI 扩展为 5–15 个变体（大小写/连字符/中英文/别称），缓存 7 天 | AI 不可用时退化为规则法（拆分+两两组合），流程不中断 |
| R-202 | 配额前置：库内查重后，先按配额截断再送 AI 分析——Twitter 源 ≤15 条/关键词/轮，其他源合计 ≤10 条 | **AI 调用量硬上限 = 25 次/关键词/轮**，配额可在设置中调整 |
| R-203 | AI 分析输出六个字段：isReal、relevance(0–100)、relevanceReason、keywordMentioned、importance(low/medium/high/urgent)、summary（说明与关键词的关联，非内容介绍） | 输入截断 2000 字符；temperature 0.2 保证一致性 |
| R-204 | 三级过滤：① isReal=false 丢弃；② relevance<50 丢弃；③ 未直接提及关键词且 relevance<65 丢弃 | 第三条是防"同领域沾边"的关键规则 |
| R-205 | AI 分析失败的内容进入待重试队列（最多重试 2 次），**不直接放行也不丢弃** | 修正 1.0"失败即放行"的漏洞 |
| R-206 | AI 结果缓存：同一内容哈希的分析结果缓存 30 天，跨关键词复用 | 降本 |
| R-207 | AI 服务未配置时：全流程仍可运行，分析字段使用降级默认值并在界面上明确标识"未经 AI 审核" | 可用性兜底 |

### 4.3 通知规则

| 规则 ID | 规则 | 说明 |
|---|---|---|
| R-301 | 每条新热点：写入通知中心 + WebSocket 实时推送（按关键词房间定向 + 全局广播） | 前端即时插入列表头部并 toast 提示 |
| R-302 | 邮件仅对 importance ∈ {high, urgent} 的热点发送 | 防邮件轰炸；阈值可配置 |
| R-303 | 数据源连续失败 ≥3 轮：产生 alert 类型系统通知 | 让用户感知"监控哑了" |
| R-304 | 通知支持：单条已读、全部已读、单条删除、清空 | 同 1.0 |

### 4.4 排序与展示规则

| 规则 ID | 规则 | 说明 |
|---|---|---|
| R-401 | 热度分全局唯一口径：`likes×10 + retweets×5 + log10(views)×2`，落库时预计算 | 排序与展示使用同一数值，消灭 1.0 的双份公式 |
| R-402 | 重要性排序：urgent > high > medium > low，同级按时间倒序 | 数据库直接排序，支持分页 |
| R-403 | 前端"热度等级"标签（爆/热/温）由后端返回归一化分值驱动 | 展示与排序不矛盾 |

## 五、功能需求详述

> 优先级：**P0** = 上线必须；**P1** = 上线后第一个迭代；**P2** = 视资源排期。

### FR-1 关键词管理（P0）

**用户故事**：作为用户，我要管理我的监控关键词，以便控制系统帮我盯什么。

| # | 需求 | 验收标准 |
|---|---|---|
| FR-1.1 | 创建关键词（文本 + 可选分类） | 空文本/纯空格拒绝；重复关键词返回 409 并提示；创建成功即开始订阅其 WS 房间 |
| FR-1.2 | 关键词列表展示（文本、分类、激活状态、累计热点数、创建时间） | 列表含每个关键词的热点计数 |
| FR-1.3 | 激活/暂停切换 | 暂停的关键词在下轮检查中被跳过（R-101） |
| FR-1.4 | 编辑与删除 | 删除需二次确认；删除关键词不级联删除已产生的热点（热点保留，关联置空） |

### FR-2 热点信息流 Dashboard（P0）

**用户故事**：作为用户，我要在一个信息流里看到系统为我发现的所有热点，并能多维度筛选排序，快速找到最值得看的内容。

| # | 需求 | 验收标准 |
|---|---|---|
| FR-2.1 | 统计概览：累计热点、今日新增、urgent 数量、按来源分布 | 数据与 `/stats` 一致；首屏 SSR 直出，LCP ≤2.5s |
| FR-2.2 | 热点卡片：重要性徽章、来源图标、AI 摘要（标注"AI 摘要"）、作者信息（含认证标）、相关性分、热度分与等级标签、互动数据（点赞/浏览等按源展示）、发布时间（相对时间）、原文链接 | 热度分与排序口径一致（R-401/R-403）；可疑内容（isReal=false 的历史数据）展示"可疑"标 |
| FR-2.3 | 可展开查看：AI 相关性打分理由、原始内容全文 | 支持单条展开与一键全部展开/折叠 |
| FR-2.4 | 筛选：来源、重要性、关键词、时间范围（1h/今天/7天/30天/自定义区间）、真实性 | 筛选条件映射为 URL 参数，刷新/分享链接后状态保持 |
| FR-2.5 | 排序：最新（发现时间）、发布时间、相关性、重要性、热度 | 全部为数据库排序+真分页（修复 1.0 全表内存排序）；分页器展示总页数 |
| FR-2.6 | 实时更新：收到新热点推送时列表头部插入 + toast | WS 断线指数退避重连；重连后自动全量刷新一次 |
| FR-2.7 | 删除单条热点 | 二次确认；删除后通知中心关联通知不报错 |

### FR-3 全网搜索（P0，异步化改造）

**用户故事**：作为用户，我要临时搜一个还没监控的关键词，快速看到多源聚合结果和 AI 判断。

| # | 需求 | 验收标准 |
|---|---|---|
| FR-3.1 | 输入关键词，从 Twitter + Bing 聚合搜索，前 10 条结果附 AI 分析（真实性/相关性/重要性/摘要） | 搜索结果不落库 |
| FR-3.2 | **异步任务化**：提交后立即返回任务受理（≤1s），结果通过 WS 推送或轮询任务状态获取 | 修复 1.0 同步等待数十秒的问题；任务有明确状态（排队/运行/完成/失败）与超时（默认 120s） |
| FR-3.3 | 搜索结果支持同样的筛选排序 | 复用筛选排序组件 |
| FR-3.4 | 搜索结果一键转为监控关键词 | 减少从"临时搜"到"长期盯"的转化成本 |

### FR-4 通知中心（P0）

| # | 需求 | 验收标准 |
|---|---|---|
| FR-4.1 | 通知铃铛 + 未读角标；下拉面板展示最近通知 | 收到 WS 全局通知时角标实时 +1 |
| FR-4.2 | 通知类型：hotspot（新热点，可跳转详情）、alert（系统告警，如源失效） | alert 类型有差异化样式（R-303） |
| FR-4.3 | 已读/全部已读/删除/清空 | 同 1.0 |

### FR-5 邮件通知（P0）

| # | 需求 | 验收标准 |
|---|---|---|
| FR-5.1 | SMTP 配置（host/port/账号/授权码/收件人）通过环境变量配置 | 未配置时静默跳过且不影响主流程 |
| FR-5.2 | 高重要性热点发送 HTML 邮件：标题、重要性徽章、AI 摘要、来源、相关性分、关键词、发现时间、原文按钮 | 仅 high/urgent（R-302）；邮件内容经模板转义，防 XSS |
| FR-5.3 | 邮件发送失败仅记日志，不重试不阻塞 | 单热点邮件失败率可容忍 |

### FR-6 数据源健康面板（P0，新增）

**用户故事**：作为用户，我要知道每个数据源是不是还活着，以便信任"监控没有哑掉"。

| # | 需求 | 验收标准 |
|---|---|---|
| FR-6.1 | 展示 6 个数据源的状态卡：最近成功时间、连续失败次数、最近错误信息 | 数据来自 SourceHealth；连续失败 ≥3 标红 |
| FR-6.2 | 源连续失败 ≥3 轮时产生 alert 通知（R-303） | 告警去重：同一源恢复前不重复告警 |
| FR-6.3 | 健康数据提供只读 API | 供面板与外部监控复用 |

### FR-7 系统设置与鉴权（P0）

| # | 需求 | 验收标准 |
|---|---|---|
| FR-7.1 | 全部 API 需携带有效凭据（API Key） | 无凭据/错误凭据返回 401；WS 握手同样校验 |
| FR-7.2 | 运行时配置：检查周期、AI 配额（Twitter/其他）、邮件通知重要性阈值 | 存 Setting 表，修改后下一轮生效，无需重启 |
| FR-7.3 | 手动触发全量检查按钮 | 锁占用时按钮禁用并提示"检查进行中"+ 当前进度（正在处理第 N/M 个关键词） |

### FR-8 Agent Skills 技能包同步（P1）

| # | 需求 | 验收标准 |
|---|---|---|
| FR-8.1 | Skill 包采集脚本与后端 collectors 同源（共享代码或定期同步） | 单一实现，不再双语言两份 |
| FR-8.2 | SKILL.md 报告模板与 2.0 的字段口径对齐（热度分、重要性定义） | 技能包输出报告与 Web 端展示一致 |

## 六、非功能需求

| 类别 | 需求 |
|---|---|
| 性能 | Dashboard 首屏 LCP ≤2.5s；热点列表接口 P95 ≤500ms（10 万条热点数据量下）；单关键词单轮检查端到端 ≤5 分钟（含 AI 分析） |
| 成本 | AI 调用硬上限 25 次/关键词/轮（R-202）；缓存命中率随关键词重叠度提升，目标整体 AI 成本较 1.0 同负载下降 ≥30% |
| 可靠性 | 定时任务 30 分钟周期完成率 ≥99%；单源故障隔离；任务崩溃后下一轮自动恢复，无需人工介入 |
| 安全 | 全 API 鉴权；邮件/页面输出转义；URL 协议白名单（仅 http/https）；秘钥仅走环境变量，启动校验缺失即明确报错 |
| 可观测 | 结构化日志（每轮检查：关键词数/各源抓取数/AI 调用数/耗时）；SourceHealth 记录；支持按 run_id 追溯单轮检查全过程 |
| 兼容性 | 现代浏览器（Chrome/Edge/Safari 最近两个大版本）；桌面优先，移动端基本可用（响应式） |
| 部署 | docker-compose 一键拉起（web/api/db/redis/反代）；提供数据迁移脚本（SQLite → PostgreSQL，含历史数据与预计算字段回填） |

## 七、用户体验关键点（设计输入）

1. **信任感是核心体验**：AI 摘要必须标注"AI 摘要"；打分理由可展开查看；源健康面板公开系统状态——让用户始终能回答"系统凭什么给我推这个、它还在正常工作吗"。
2. **零打扰默认**：实时推送只 toast 不弹窗；邮件只有 high/urgent；告警去重。
3. **从搜索到监控的顺滑转化**：搜索结果页提供"加入监控"按钮（FR-3.4）。
4. **视觉延续**：保留 1.0 的暗色科技感主题与动效（光束/流星/聚光灯），用户无迁移割裂感。
5. **空状态设计**：无关键词时引导创建；无热点时展示"监控中"状态与下次检查时间，而非空白。

| M1 后端骨架 | FastAPI + SQLModel/PG、只读 API、鉴权、SQLite→PG 迁移脚本 | 旧前端指向新后端功能可用；历史数据完整迁移 | 3–4 天 |
| M2 监控流水线 | collectors 插件化、AI 层（缓存/重试/配额前置）、分布式锁调度、邮件 | 新旧系统并行灰度一轮，产出对比一致后切流；AI 调用量可审计且不超上限 | 4–5 天 |
| M3 前端重构 | Next.js 三页面、组件拆分、SSR 首屏、WS hook、筛选 URL 化 | 功能对等 1.0 前端；LCP 达标 | 4–5 天 |
| M4 增强收尾 | 搜索异步化、源健康面板、告警通知、docker-compose、CI、文档 | 一键部署；源故障 30 分钟内可感知 | 2–3 天 |

**灰度策略**：M2 期间新系统只落库不通知，与 1.0 并行跑 ≥2 轮，抽样对比同一关键词的双边产出（命中数、过滤判定一致性 ≥90%）后切换。

**上线检查单（Go/No-Go）**：鉴权全量生效 / 配额硬上限生效 / 迁移数据抽验通过 / 告警链路实测（手动断一个源）/ 回滚预案（旧系统保留 2 周可一键切回）。

## 十、度量与数据（埋点要求）

| 事件 | 维度 | 用途 |
|---|---|---|
| check_run_completed | 关键词数、各源抓取数、AI 调用数、入库数、耗时 | 成本与稳定性监控（对应目标：周期完成率、AI 上限） |

| hotspot_deleted | 热点 ID、relevance 分档 | 负反馈信号（低分内容被删多 → 阈值要调） |
| search_task_submitted / completed | 耗时、结果数 | 搜索体验与超时率 |
| source_failure | 源、错误类型、连续失败数 | 源健康与告警验证 |
